## 2. 3つの要因が実際に作れるか

| 要因 | 作り方 | 確認 |
|---|---|---|
| **A 入力方式**（テンキー／ステッパー） | アプリが**回答ごとに自動で交互に出す**。端末ごとに開始位置を乱数でずらして順序効果を相殺する | ✅ `UI_CONDS` / `peekVariant()` |
| **B「わからない」ボタン**（あり／なし） | **配布URLで便ごとに固定。** `?unknown=off` を付けると非表示 | ✅ 公開版で動作確認済み |
| **C 混雑水準**（空いている／混んでいる） | **便の時間帯で作る。** アプリ側は何もしない | ✅ 改修不要 |

要因Bを画面の中で切り替えない作りにしてある。ボタンが出たり消えたりすると参加者に気づかれ、
条件そのものへの反応（要求特性）が入ってしまうため。

割り当てのカウンタは「覗く（peek）」と「1つ進める（commit）」を分けてあり、
クラスを選んで戻ってもコマを消費しない。ラテン方格の並びが実際の回答数とずれない。

## 3. 分析に要るログが取れているか

RQ1・RQ2 で使う指標を、**いま全部記録している。追加の改修なしで分析に入れる。**

| 何を見るか | ログ上の場所 | 使う問い |
|---|---|---|
| 人数入力にかかった時間 | `summary.t_count` | H1・RQ2 |
| 最初の入力までの時間（思考時間） | `summary.t_first` | H1 |
| 値を動かしたタップ数 | `summary.taps_value` | H1 |
| 押し直し（修正）の回数 | `summary.corrections` | RQ2 |
| **「わからない」を押したか** | `context.count_unknown` | **H2** |
| **人数が未入力か** | `exact_count is null` | **H2** |
| **6段階クラス** | `congestion_class` | **RQ2 第一候補** |
| 着席／立席 | `context.posture` | 共変量 |
| 次に停まるバス停の自己申告 | `next_stop` ＋ GPS | 位置がどれだけ当てになるか |
| 操作イベント列（全タップの時刻つき） | `events` | 事後の探索 |
| 練習かどうか | `practice`（true は分析から除外） | 練習2回の切り分け |

5や10への**丸め率**と、同一便内の**回答のばらつき（ICC）**は、
`exact_count` と `congestion_class` から分析側で計算する。アプリ側の対応は要らない。

## 4. 当日、人手で残す必要があるもの

アプリは**便の番号も参加者番号も持っていない。** どちらも復元はできるが、対応表は紙で残す。

| | 復元の仕方 | 当日やること |
|---|---|---|
| どの便の回答か | 回答時刻。4便は時間帯が完全に分かれているので一意に決まる | **各便の実際の発車・到着時刻を控える**（遅延に備えて） |
| ボタンあり／なしだったか | `variant.unknown_ui` に記録済み | — |
| どの参加者か | `surveyor_id`。登録したIDが表示名に入る | **配布カードに参加者番号と本人が決めたIDを書いてもらう** |
| 群1／群2 | 対応表から | 配布カードに印刷しておく |
