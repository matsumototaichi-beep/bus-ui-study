**昼の日と夕方の日を分けて実施する。** 1便あたり参加者3名（団体に見えないため）＝1日3名。

| | 使える平日 |
|---|---|
| 10月 | 13（火）・14（水）・15（木）・16（金）・**19（月）・20（火）・23（金）** |
| 11月 | 2（月）・4（水）・5（木）・6（金）・**9（月）・10（火）・11（水）・12（木）・13（金）** |

**計16日。** 標準案（1人4乗車）は実施8日なので予備が8日、
縮小案（1人2乗車）なら実施4日で予備が12日残る。雨・欠席・遅延は吸収できる。

> ### ⚠️ 土日は使えない
> 10/24・25、11/14・15 は土日。**この4便が土休日ダイヤに存在しない。**
> 土休日は北口16時台が `17/33/48` で **16:20が無く**、
> 桃山台17時台が `北10/20/北40/50` で **17:18が無い**。
> 便を選び直すことになり、平日データと混ぜられなくなる（曜日差と条件差が分離できない）。
> **予備日からも外す。**

**どの日を昼にして、どの日を夕方にするかは、参加者の都合に合わせて決める。**
同じ方に昼と夕方の両方へ来てもらえれば、混雑水準（要因C）が被験者内になって望ましい。
都合がつかない方は片方だけでも構わない（2026-09-24 松本の判断）。

## 4. 条件の割り付け

> ### ★2026-09-26 変更：入力方式は「実施日ごとに固定」する
> 旧版はアプリが1回答ごとに入力方式を入れ替えていた。それだと参加者は「さっきの画面」を
> 特定できず、事後アンケートで**画面の写真を貼って見比べさせる**しかなかった。
> **日ごとに固定すれば「その日ずっと使っていた方式」として思い出せる。写真が要らなくなる。**
> 副産物として、**1本目と2本目の違いが「わからない」ボタンの有無だけ**になる。

**要因A（入力方式）** は実施日ごとに固定する。**要因B（「わからない」ボタン）** は便ごとに固定する。
どちらも配布URLで決まる。**要因C（混雑水準）** は日で決まる。

### 割付表

| | 昼の日（空いている） | | 夕方の日（混んでいる） | |
|---|---|---|---|---|
| | **1本目** 12:49 | **2本目** 13:48 | **1本目** 16:20 | **2本目** 17:18 |
| **群1**（組1・組3） | ステッパー＋**あり** | ステッパー＋**なし** | テンキー＋**なし** | テンキー＋**あり** |
| **群2**（組2・組4） | テンキー＋**なし** | テンキー＋**あり** | ステッパー＋**あり** | ステッパー＋**なし** |

**入力方式は1日を通して変わらない。** 群1は昼＝ステッパー／夕方＝テンキー、群2はその逆。

### 配布URL（4通り。QRポスターも4枚）

土台は `https://matsumototaichi-beep.github.io/bus-ui-study/`

| ポスター | 条件 | 付けるパラメータ |
|---|---|---|
| **A** | ステッパー＋ボタンあり | `?input=stepper` |
| **B** | ステッパー＋ボタンなし | `?input=stepper&unknown=off` |
| **C** | テンキー＋ボタンあり | `?input=numpad` |
| **D** | テンキー＋ボタンなし | `?input=numpad&unknown=off` |

| | 昼1本目 | 昼2本目 | 夕1本目 | 夕2本目 |
|---|---|---|---|---|
| **群1** | **A** | **B** | **D** | **C** |
| **群2** | **D** | **C** | **A** | **B** |

**1日に使うポスターは2枚だけ**（その日の入力方式のぶん）。4枚とも持っていき、当日2枚を使う。

### この割り付けで釣り合うこと

- どの参加者も、4乗車で**入力方式2 × ボタン2 の4通りを1回ずつ**経験する
- どの参加者も、**空いている便と混んでいる便の両方**を経験する
- 組で昼夕を入れ替えてあるので、**全体としてはどちらの入力方式も空いている便・混んでいる便の
  両方に現れる**。入れ替えないと入力方式と混雑が完全に重なって分離できなくなる
- 条件ごとの回答数は 2×2×2 ＝ 8セルに **各48回答**（`§2.5`）

> **引き換えに失うもの。** 旧方式は同じ便の中で入力方式が入れ替わるので、
> 人・日・便・混雑をすべて揃えた対比較ができた。日ごとの固定ではそれが使えず、
> **入力方式の比較に日差・混雑差の分散が乗る**（H1の検出力が落ちる）。
> 回答数は変わらないが、同じ日の回答どうしは強く相関するため実効的な標本数は減る。
> 分析では日と参加者を変量効果に入れる（`UI_STUDY_SPEC.md` §3）。

**群は「組」単位で決める。** 3名で1組、組ごとに群を交互に置く
（組1=群1／組2=群2／組3=群1／組4=群2）。12名で群1が6名・群2が6名になり釣り合う。

> **同じ便に乗る3名は必ず同じ群にする。** 群を混ぜると、同じバスの中で
> 「わからない」ボタンが出る人と出ない人が並び、参加者に条件の存在を気づかれる（要求特性）。
> 組単位にしておけば、1便につき配布URLは1つで済む。

**どちらの群の人も、4乗車で「ボタンあり×空いている／あり×混んでいる／なし×空いている／
なし×混んでいる」を1回ずつ経験する。** 要因Bと要因Cが完全に被験者内で交差する。

事後アンケートの版（v1〜v4）は参加者番号を4で割った余りで決め、
**配布URLとは独立に**割り当てる（`QUESTIONNAIRE.md`）。

**参加者のアカウントは事前に作っておき、IDとパスワードを刷ったカードで渡す**
（2026-09-26 確定）。番号・組・群・アンケート版はすべてカードに入る。
作り方と当日の手順は `docs/login_prep.md`。

## 5. 乗り間違いを防ぐ

桃山台駅〜阪急南千里駅〜亥子谷の区間は **2・3・5・8・9・10・11 の7系統が重なる**。
とくに3系統は2系統と起終点が同じ（ＪＲ吹田駅（南口）⇔桃山台駅）で吹田側の経路だけが違うため、
乗り間違えるとデータ上で見分けがつかない。

> ### ⚠️ 桃山台では「北口ゆき」に乗ってはいけない（2026-09-25 訂正）
>
> 当初この節に「桃山台では行先番号[2]と**『ＪＲ吹田駅（北口）ゆき』**を目視確認」と書いていたが、
> **これは誤りだった。** 現行の停留所時刻表（桃山台駅2番のりば・2026年4月1日改正）で判明：
>
> - **[2] の行先表示は「ＪＲ吹田駅（南口）」。** 使う17:18発・13:48発はどちらも
>   `北`（＝北口止まり）の印が無く、南口まで行く便なので、方向幕は「南口」と出る
> - **「ＪＲ吹田駅（北口）」と表示して出るのは [5]**（原町二丁目経由）という別系統
>
> つまり「北口ゆき」を探すと **[5] に乗ってしまう。**

| | 対策 |
|---|---|
| **北口発（両日とも1本目）** | **①のりばに並べばよい。3系統は北口を通らない**ので、取り違えが構造的に起きない |
| **桃山台発（両日とも2本目）** | **2番のりばで「[2] ＪＲ吹田駅（南口）ゆき」に乗る。降りるのは北口。** 「ＪＲ吹田駅（北口）」と出ているバスは [5] で、乗ってはいけない。とくに昼は毎時 `:24` 発が3系統で、**北口を通らない**ので絶対に乗せない |
| 共通 | 「実験者が指定した1本にだけ乗る。来た順に乗らない」と説明で明示する |

桃山台駅2番のりばには **[2][3][5][8][9][10][11][61][62][65][69]** が集中している。
**当日いちばん事故りやすいのはここ。**

**便の指定は系統番号だけでは足りない。** 同じ2系統でも運行区間が便ごとに違う
（南口まで行く便／北口で終わる便／亥子谷止まりの便）。
**起点・発車時刻・行先**をセットで指定すること。

## 6. 基準値（計数役）

前扉・後扉に1名ずつ。記録用紙は `docs/counting_sheet.html`（A4片面・1便1枚・係ごとに1枚）。

**今回選んだ4便はすべて始発便なので、車内0人から積み上げられる。**
先行実験（2026-09-18）で、終点で車内人数がちょうど0に閉じることを実証済み。

終点で「乗車合計 − 降車合計 ＝ 0」を2人で突き合わせる。
0にならない便は**基準値なしとして捨てる**（無理に合わせない）。

夕方2本目（17:18発）は混雑で目視が崩れる前提。**ここで得られるのは正解ではなく参照値**である
（先行実験で最大10人ずれた）。RQ2・RQ3はその前提で組んである。
