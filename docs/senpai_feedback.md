#### 先輩の懸念は寸法でもデータでも裏付けられた

`.stepper` は7列（`repeat(3,1fr) 1.7fr repeat(3,1fr)`）。ボタン1個の実測幅：

| 端末 | 現行（±1/5/10） | ±1/5 の場合 |
|---|---|---|
| 320px (SE1) | **35.3px** | 49.1px |
| 375px (SE2/SE3) | **41.7px** | 58.1px |
| 390px (iPhone 14) | **43.1px** | 59.9px |

Apple HIG の 44pt を全機種で下回る。旧版は58×58pxだったので SE1 で面積52%減。
`DESIGN_PHILOSOPHY.md` の原則 A7「Apple HIG の最小タッチ領域（44pt）に準拠」に反している。
PCブラウザでは50.6pxで基準を満たすため見落としやすい。

±10 を足した根拠（変更台帳「大人数時の操作回数削減」）を実測データで検算：

```

n=6597  中央値6人  最大75人
class1 46.6% / class2 29.8% / class3 9.2% / class4 12.9% / class5 1.3% / class6 0.2%

初期値 lo から目標値までの平均タップ数
  ±1/5/10 = 1.983    ±1/5 = 2.011    差 = 0.028タップ
  ±10 が1タップでも減らす回答 = 2.8%（186/6597）
```

**全ボタンを3割狭くする代償に対し、削減は平均0.03タップ。** 変更台帳の根拠は成立していない。
（このデータを卒研の判断材料に使ってよいかは研究室の確認が要る認識。`EXPERIMENT_PLAN.md` §6 参照）

#### 卒研への波及

`UI_STUDY_SPEC.md` は自前テンキー採用の利点として「ボタンサイズを統制できる」と書いているが、
統制されているのはテンキー内部だけで条件間では統制されていない：

- 375px：テンキー 92.7×44px（4,077px²）vs ステッパー 41.7×50px（2,086px²）＝**約2倍**
- 320px：93.3×44px vs 35.3×46px ＝**約2.5倍**

H2（stepper vs numpad）でステッパーが不利に出ても、入力方式の差か Fitts の法則どおり
標的が小さいだけかを分離できない。→ 2段階に戻した結果、面積比は **375px 1.40倍／320px 1.82倍**まで縮んだ。
**ただし解消はしていない。** ステッパー（横4ボタン）とテンキー（3×4グリッド）は形が違うので
完全には揃えられない。方法章に限界として書いたうえで、`screen_view` にボタン実寸
（`ctl_w`/`ctl_h`）と画面サイズを記録し、解析で統制できるようにした。

## 4. 今回の点検で直した、先輩の指摘外の不具合

**幽霊レコード。** 人数入力中にヘッダーの「報告」タブや「EN」を押すと、
`renderMain()` に `answering`/`pending` のガードが無いため
(a) 入力中の値が消失 (b) `answering=true` のまま取り残され
(c) 次のクラス選択で `exact_count=null` の行が**画面ログに出ないまま送信される**、
という経路があった（`2ecb2f7` / `c21e2e2` で修正）。

先輩に動作確認を頼むなら、これが直っている版でないと説明のつかない行が増える。

**版番号の表示。** どの版を見ているか画面から分からず、
「直っていません」「直っています」の水掛け論になりうるため、
下部ステータスバーに `phaseA-1.7` / `uiStudy-0.7.2` を常時表示するようにした。

⚠️ **本体アプリには練習モードが無い**（卒研側には `practice` フラグがある）。
先輩が試した回答は本番 `responses` にそのまま入る。依頼するなら除外の段取りを先に決める。

## 5. 値域の根拠 — 訂正が必要

先輩への返答は「**バスの座席数と最大乗車数などから概算**」だったが、
**その計算の記録が両リポジトリのどこにもない**（座席／定員／capacity／閾値 すべて0件。
`supabase_responses.sql` が参照する `PROJECT_SPEC.md` も存在しない）。

唯一の関連記述は `DESIGN_PHILOSOPHY.md` §1-B の B7：

> クラスの区切り（0-5／6-15／16-25／26-40／41-55／56-）｜**元研究（BLE）の都合で決めた区切り**

ところが元研究（BLE）の混雑度区分を実際に確認すると **`0-5 / 6-10 / 11-20 / 21-30 / 31人以上` の5段階**で、
アプリの6段階とは境界も段数も一致しない。

**つまり「座席数から概算」も「BLEの都合」も、どちらも裏が取れない。**
自力で復元できないので、先輩に訂正したうえで元研究の区分の出所を尋ねるのが早い
（同じ研究室なので知っている可能性がある）。

卒論審査・学会発表で確実に聞かれる箇所。しかも卒研の `median` 条件のプリセット値は
この数値から計算されるので、**独立変数の定義がこの未確認の数値に依存している**。
