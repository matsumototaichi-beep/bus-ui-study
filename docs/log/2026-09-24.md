## 1. ログインを ID＋パスワードに変更（`uiStudy-0.8.0`）

**松本の指示**：「ログインは設定をややこしくしてもしょうがないので、今のままで、メルアドでの設定をなくして、
適当にIDとパスワードを決めてもらうようにしましょう。」

前案（事前に12名分のアカウントを作り、4文字の参加者コードを配る）は採らなかった。
コードとパスワードが1対1に決まるため「他人になりすまして送れる」状態になり、
かつ配布物の管理という当日の作業が増えるため。

| 変えたところ | 内容 |
|---|---|
| 入力欄 | メールアドレス欄・表示名欄を削除し、**ID（半角英数3〜20字）とパスワード（6字以上）の2つだけ**に |
| 確認メール | 使わない。`display_name` にはIDをそのまま入れる |
| 「パスワードを忘れた方」 | 画面から外した（メール前提のため）。`reset`/`newpass` のコードは残置 |
| バリデーション | ID書式とパスワード長を**通信前に**クライアント側で弾く（`ID_RE`、6文字） |
| 最小パスワード長 | 8 → **6**（バス停でその場で決めるため） |

実装は既存の `normLogin()`（"@" を含まない入力に固定ドメイン `id.local` を補う。
もともと共有管理者アカウント用）を参加者にも使い回しただけ。Supabase 側はメール＋パスワードのまま動く。

> ### ⚠️ 必要な設定作業
> **Supabase の Authentication → Confirm email を OFF にすること。**
> ON のままだと `@id.local` 宛に確認メールが飛び、参加者は永久にログインできない。
> 設定漏れに当日その場で気づけるよう、ID方式で確認待ちになった場合は専用の文言を出すようにした。

**検証**：ローカルサーバ（127.0.0.1:8777）＋375×812で実測。ログインタブ・新規登録タブとも欄は2つ。
ID `ab` で書式エラー、パスワード `123` で長さエラーが通信前に出る。コンソールエラーなし。

## 3. 事後アンケートを v2.0 へ全面改訂

`QUESTIONNAIRE.md` は v1.0 のまま、**旧・要因B「初期値（none / median）」を前提**に書かれていた。
S2 の4条件表（UI-A〜D）と S4（アンカリングの自覚）が実態と合っていなかったので作り直した。

### 要因ごとに聞き方を分けた
| 要因 | 参加者の経験 | 聞き方 |
|---|---|---|
| A 入力方式 | 1乗車の中で何度も入れ替わる | **S2** で2つを直接比較（8問。旧版は16問） |
| B 「わからない」ボタン | 1本目と2本目で片方ずつ | **S4** で最後に聞く |

**S2 と S4 の間に壁を置くのが肝。** 4条件の画面を最初にまとめて見せると、
ボタンの有無という違いにその場で気づいてしまい、S3（回答行動の自己報告）が汚染される。
S2 では入力方式の2枚だけを見せ、S4 に入って初めてボタンあり／なしの2枚を見せる。

新設した **S3-3「数えきれていないのに、それらしい数を入れて送ったことがありますか」** が核心。
H2 が想定する「ボタンが無いと偽のラベルが混ざる」を本人の申告から裏づける設問で、
先行実験（2026-09-18）で松本自身に起きた現象そのもの（数えられないまま 0人 として3件送信）。

### フォームの版（4版）
S2・S4 とも「2つを並べて比べさせる」ので、先に見せたほうが有利に評価されうる。提示順を入れ替える。

| 版 | S2 の提示順 | S4 の提示順 | 割り当て |
|---|---|---|---|
| v1 | ステッパー → テンキー | あり → なし | P01・P05・P09 |
| v2 | テンキー → ステッパー | あり → なし | P02・P06・P10 |
| v3 | ステッパー → テンキー | なし → あり | P03・P07・P11 |
| v4 | テンキー → ステッパー | なし → あり | P04・P08・P12 |

設問は全版同一で、**画像と選択肢の並び順だけ**が違う。参加者番号を4で割った余りで機械的に決める。
どの版かは設問 0-3 として持たせ、集計時に取り違えないようにする。
版は**配布URL（要因Bの水準）とは独立**に割り当てる。

## 4. 残っている論点

### ① 練習2回をどこでやるか（松本の確認待ち）
松本の希望は「バス乗車中に2回」。ただし走行中にやると、
**1乗車のうち最も混んでいる序盤（発車直後）のデータが練習で潰れる。**
始発から乗るので混雑のピークは発車直後にきて、H3（混雑時ほど効果が大きい）の
検証材料が最初に削られる。松本自身も「最初の方の情報が0になってしまう」と指摘している。

**提案：始発停留所に停車中の車内で2回。**
2系統は JR吹田駅（北口）・桃山台駅ともその停留所が始発なので、発車前に乗り込んで着席した状態で練習できる。
実機・実車内・実際の乗客という条件は満たしたまま、走行中の本番データを1つも失わない。
練習は本番の条件カウンタを進めない実装（`uiStudy-0.7`）なので、条件割当はずれない。

### ② 計数役を全便に入れるか、一部の日だけにするか
`EXPERIMENT_PLAN.md` §2 の R2（乗降フロー計数）の実施規模。全便に入れると人手と運賃が増える。
松本の「乗車人数は3人で回します」が **参加者3名** を指すのか
**参加者＋計数役で計3名** を指すのかで話が変わるため、確認待ち。

### ③ 計数役2名の運用 → 取り決めを確定し、記録用紙を作成
役割を「乗車係＝乗った人だけ／降車係＝降りた人だけ」に固定。運転士は含めない。
数え落としは「？」を書いて先へ進み、あとから直さない。終点で
「乗車合計 − 降車合計 ＝ 0」を2人で突き合わせ、**0 にならない便は基準値なしとして捨てる**（無理に合わせない）。

記録用紙は `docs/counting_sheet.html`（A4縦・片面・1便1枚・係ごとに1枚）。
ブラウザで開いて印刷する。1枚目（桃山台駅→ＪＲ吹田駅北口）は下見で確認した18停留所を印刷済み。
**2枚目（ＪＲ吹田駅北口→桃山台駅）は停留所名が空欄**。この方向の停留所順は下見で確認できていないため、
公式時刻表で並びを確認してから記入すること（未確認の並びを刷ると計数役が行をずらして記録する）。
