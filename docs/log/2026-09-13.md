## やったこと：条件の開始位置を実験者が指定できるように（`03e1a7a` / uiStudy-0.6）

`EXPERIMENT_PLAN.md` §3.1 の要改修項目。`HANDOFF.md` §7・§9-3 に「要改修」として残っていたもの。

### 何が問題だったか

開始位置は `condOffset()` が**端末ごとにランダム**に決めて localStorage に保存していた。
これだと同じ便に乗った参加者同士で開始位置が偶然一致し、**同じ瞬間に同じ条件**になりうる。
計画の柱である「同じ便・同じ瞬間を違う条件で見る（＝便の混み具合・車両・運転手の違いを条件間で相殺する）」が崩れる。
真値が無い本研究では、この相殺が主張の土台なので影響が大きい。

### どう直したか

実験バー（報告画面の上部）に **「参加者」番号**の欄を追加した。実験コード・着席/立席と同じ並び。

- 開始位置 = `(参加者番号 - 1) mod 4`
- 参加者番号は実験コードと同様に**日付で失効**（前日の番号が残ったまま別人に使われるのを防ぐ）
- 未設定なら従来どおり端末ごとのランダム（下見・パイロット・単独テスト用のフォールバック）
- ログに `variant.participant` と `variant.offset_src`（`participant` / `random`）を記録。
  **解析時に「ラテン方格が実際に効いていたか」を判別できるようにするため**
- 参加者番号を変えたら試行カウンタ `seq` を 0 に戻す。
  計画書 §3.2-3 の統制変数「何回目の回答か」に前の参加者の回数が混ざるのを防ぐ

### 確認したこと

実機相当（375×812 / 320×568）のブラウザで検証。

割り当ての実測：

```
           1回目             2回目             3回目             4回目
参加者1    stepper/none     numpad/median    stepper/median   numpad/none
参加者2    numpad/median    stepper/median   numpad/none      stepper/none
参加者3    stepper/median   numpad/none      stepper/none     numpad/median
参加者4    numpad/none      stepper/none     numpad/median    stepper/median
参加者5    （参加者1と同じ＝4人周期）
```

**どの列（＝同じ瞬間）でも参加者1〜4の条件が重ならない。** 計画書 §3.1 の図のとおり。

その他：
- 未設定時 → `offset_src=random`, `participant=null` に落ちる
- 入力の整形：`07a` → `7`（英字除去・先頭ゼロ除去、2桁まで）
- 参加者番号を変更 → `seq` が 7 → 0 に戻る
- 通しで1回答 → 保存されたセッションに `variant.participant=2` / `context.participant=2`（型も数値で統一）
- 実験バーが3要素になったので折り返しを許可。320×568 でもはみ出し 0、クラスカード6枚は画面内に収まる

※コンソールに出る `ui_sessions insert失敗（PGRST205）` は既知。Supabase のテーブルが未作成なので送信は失敗し、localStorage にのみ残る（NAIST 側を汚さない安全側）。今回の変更とは無関係。

## 追加：教授報告のレビューを受けた計画の全面見直し

松本から4点の指摘。うち②は**こちらの記述が誤り**だったので訂正した。

### ① パイロットとは
本番と同じ手順を1〜2名で通してみるリハーサルのこと（練習生・デモンストレーターではない）。
**実施するかは未定**として計画書・費用試算から外した。

### ② 帰属の論理が誤っていた（最重要）
旧：「同じ便・同じ瞬間に複数の参加者が違う条件で答えるので、差はUIのせい」
→ **成立しない。答える人が違えば差は人のせいかもしれない。**

新（`EXPERIMENT_PLAN.md` §3.1 を全面差し替え）＝**二重差分**：
1. 同じ人が同じ1回の乗車の中で両条件を経験する（人の癖が消える）
2. 同じ区間で参加者A・Bの条件を完全に反転させる（その瞬間の混雑が消える）

言い方も変えた。「乱数で割り当てたから平均すれば相殺される」ではなく
「各参加者が両条件を同数経験し、各瞬間に両条件が同時に存在するよう**構成した**ので、
人の癖もその瞬間の実状況も差分で打ち消される」。12名で偶然の釣り合いに頼るのは弱すぎる。

**分析単位を「停留所」から「区間」に変更**。ドアが閉まっている間は車内人数が物理的に一定なので、
「停留所 i を発車〜i+1 到着」を1機会とし、走り出してから答えてもらう。

⚠️ **アプリの改修が必要（未着手）**。現在は「何回目の回答か」で条件を進めるため、
1か所答え損ねると以降が全部ずれて 2 の反転が崩れる。**停留所IDに固定した割当表**に変える（`uiStudy-0.8`）。
＝9/13 に入れた参加者番号ベースの仕組みは、考え方は合っているが**単位が違う**ので作り直し。

### ③ 乗降カウントは2人以上必要 → 主計画から外した
指摘のとおり混雑時に1人で両ドアは見られない。加えて検討で判明したこと：
- 絶対値を出すには空の始発から終点まで乗り通す必要がある（途中乗車だと初期人数が不明）
- **最も知りたい混雑時（クラス5〜6）で最も計数が成立しない**
- 2名追加で費用 +2.4万円、1便あたりの人数制限にも抵触

→ **基準値は H1〜H3 の検証には不要**（交絡を除いているのは §3.1 の二重差分）。
主計画から外し、人手が確保できたらボーナス扱いに格下げ。

### ④ 松本本人が参加も計数もできない
計数を主計画から外したので、**追加の人員は不要**になった。
費用は 21人日→18人日、約8.4万円→**約7.2万円**に下がった。

### 検討で新たに出た論点（計画書に反映済み）
- **「アンカリング」と言い切れない**：ステッパーでは初期値が「目標値までのタップ数」を決めるので、
  心理的な引き寄せがゼロでも操作コストの差だけで同じ結果が出る。
  → 「初期値提示によるバイアス（アンカリング＋到達コストの合成）」と定義し直した。
  切り離せるのは**テンキー条件での初期値ぴったり一致率**のみ
- **H3 は尺度の交絡**：クラス幅が上位ほど広いので人数単位だと機械的に大きく出る。→ 正規化必須
- **`none` もアンカーはある**：6クラス自体が人数レンジ表示。操作しているのは点アンカーの上乗せだけ
- **スキップによる選択バイアス**：`median` は1タップで確定できるのでスキップが減る。
  → スキップ率を主要な結果の1つにし、「わからない」を明示的に選べるようにする（任意性は維持）
- **H2（入力方式）の帰属は弱い**：乗車単位で固定するので人内の対比が1ペアしかなく、
  時間帯・疲労と同居する。→ 主張を降格
- **go/no-go 日を設定**：倫理審査は4〜8週かかりうる。10月末までに許可が出なければ代案へ
- **代案2＝室内版**（画像提示）を保険ではなく積極的な選択肢に格上げ。
  画像なら**真値が既知**なのでバイアスの向きまで言える
